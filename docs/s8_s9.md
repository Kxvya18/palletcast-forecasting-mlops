# S8–S9 · Retraining and CI/CD

## S8 · Retraining policies

**Question:** after the 2026 changes (S02's new customer and Saturday shift, S04's hidden
contract loss), which retraining policy works best?

| Policy | Rule |
|---|---|
| frozen | keep the 1 April production model (v7) |
| monthly | retrain on the first Monday of every month |
| triggered | every Monday, retrain if any site's last-week WAPE > 18% or \|bias\| > 10% (at most every 14 days) |

Every retrain goes through the S4 gate. Models train only on labels final on the retrain day
(21-day rule). Same start model, same April–September 2026 forecasts for all policies.
Code: `retraining/experiment.py`; results: `reports/s8/`.

**Results**

| Policy | WAPE | Bias | Retrains | Rejected by gate |
|---|---|---|---|---|
| frozen | 10.30% | −1.6% | 0 | – |
| monthly | 10.27% | −0.3% | 6 | 1 |
| triggered | 10.23% | −0.4% | 10 | 4 |

S04 bias after the hidden contract loss (June / July / August): frozen +11.9% / +4.9% / +4.0%;
monthly +11.4% / +4.9% / +4.2%; triggered +11.4% / +4.6% / +4.3%.

**Reading it honestly:**
1. **Accuracy barely differs** (0.07 points between best and worst). The recent-history
   features (same-weekday lags, 28-day means) adapt on their own after a change, which is why
   even the frozen model recovers on S04 from +12% to +5% within a month.
2. **Retraining can't react faster than the 21-day label rule allows.** A new situation can
   only be learned once 3 weeks of it are final. Training on not-yet-final labels would be
   faster but leaks future corrections (S2).
3. **The real benefit is bias:** retrained models remove the slow drift into under-forecasting
   (−1.6% → about −0.3%).
4. **Triggered retraining is noisy:** 10 retrains, 4 rejected by the gate. One week of data is
   a jumpy signal.

**Decision:** keep **monthly retraining with the gate** (the S5 flow). It's simple and
predictable and fixes the bias drift; alert-triggered retraining adds complexity for no
measurable gain here. Alerts (S7) stay, as a signal for *people* to investigate, e.g. an
unrecorded contract loss.

Compared with S3's experiment E5 (monthly beat quarterly by 0.45 points in 2025): there the
alternative was 3 months without a refresh during a growth period. Here the start model was
already fresh and the period mostly stable, so the gap is smaller. Both point the same way.

## S9 · CI/CD (GitHub Actions)

**CI**: `.github/workflows/ci.yml`, on every pull request and every push to `main`:

| Job | What it checks | Time |
|---|---|---|
| `fast` | ruff lint; backtest metrics, promotion gate rule, drift parsing | ~2 min |
| `pipeline` | full-size simulate → validate → features; every planted fault caught; no leakage | ~9 min |
| `docker` | the service image (code + core dependencies) still builds | ~3 min |

`fast` and `pipeline` run in parallel, so feedback on a broken change arrives in about 2
minutes. The API-equals-offline test (`tests/test_serving.py`) needs the local registry and
data, so it runs locally (skipped in CI).

**CD**: `.github/workflows/release.yml`, only when a version tag is pushed
(`git tag v1.0 && git push --tags`). Builds the service image and publishes it to GitHub's
container registry as `ghcr.io/<owner>/palletcast-forecast:<tag>`. In a team setup the container
loads the production model from a shared MLflow server at start-up (`MODEL_URI`,
`MLFLOW_TRACKING_URI`), so promoting a model doesn't need a new image.

## What a real deployment would add
- A shared MLflow server and artifact store instead of the local SQLite file.
- A Prefect deployment with the monthly schedule (`monthly_run.serve(cron="0 7 1 * *")`)
  running on a server.
- Prediction intervals for planners, and an alert channel (e.g. a message to the planning
  team) for S7 alerts.
